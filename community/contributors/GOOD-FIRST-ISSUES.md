# Good first issues

A suitable beginner issue has one bounded objective, a public-safe input, a named
file area, explicit acceptance criteria and a short verification command. Prefer
small documentation corrections, missing edge-case tests and synthetic fixture
improvements. These are candidate categories, not claims that live issues exist.

Maintainers should supply prerequisites, explain expected behavior, identify
out-of-scope work and avoid changing the goal after work starts. Check with the
owner before applying GitHub labels; this documentation modifies no remote settings.
Do not assign production incidents, historical secret cleanup, private research
or proprietary algorithms to a beginner. Offer feedback without time/participation
promises that the project cannot fulfill. Limit one active issue per newcomer by
agreement; avoid collecting personal profile information in the issue.
